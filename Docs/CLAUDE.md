# 응답 언어

- 채팅 답변은 항상 한글로 작성한다. (코드/식별자/커밋 메시지 등은 예외)

# 커밋 메시지 규칙

- 항상 2줄 이하로 작성한다.
- 대화하듯 설명하지 않는다 (예: "~를 수정했습니다", "이유는 ~때문입니다" 같은 문장형 설명 금지).
- 1번째 줄 맨 앞에 커밋 종류를 붙이고 콜론으로 구분한다: `feat`(기능 추가), `fix`(버그 수정), `refactor`(동작 변화 없는 구조 개선), `merge`(브랜치 병합), `chore`(설정/에셋 정리 등 그 외 잡무).
- 그 뒤에 이번에 한 것 / (필요하면) 다음에 할 것, "/"로 구분.
- 2번째 줄(선택): 꼭 알아야 할 주의사항 1개만, `*`로 시작.

예시:
```
feat: 좌표/로테이션 동기화 테스트 완료 / 발사체 동기화 진행 예정
*Projectile은 현 버전에서 온라인에 의존, 오프라인 테스트 따로 생성 예정
```

# 코드 스타일

- 주석은 "왜"만 남기고 "무엇"은 남기지 않는다. 식별자 이름으로 이미 알 수 있는 내용은 주석으로 반복하지 않는다.
- "이번에 고친 이유", "~ 때문에 추가함" 같은 현재 작업/이슈 맥락을 주석에 남기지 않는다. 코드가 나중에 그 맥락과 무관해져도 주석은 계속 남아 잘못된 정보가 된다.
- 주석은 1줄 이내로 짧게. 여러 줄짜리 설명이 필요하면 애초에 코드/구조를 더 명확하게 만드는 쪽을 먼저 고려한다.
- 과도한 추상화, 나중을 대비한 범용 인프라(제네릭 풀링 시스템 등)를 미리 만들지 않는다. 지금 필요한 만큼만 구현하고, 실제로 필요해지면 그때 확장한다.

# Unity 프로젝트 구조/컨벤션

1. `GetComponent`/`GetComponentInParent`/`GetComponentInChildren` 같은 런타임 참조 검색을 지양한다. 최대한 에디터에서 인스펙터로 직접 참조를 연결해두고, 코드는 그 참조를 캐싱만 한다.
2. `AddComponent`, `new GameObject(...)`, `Instantiate` 같이 런타임에 생성/할당하는 방식을 지양한다. 최대한 에디터에 미리 배치해서 로드해두거나, 풀링 방식을 채용한다.
3. 씬 무관 영속 매니저(사운드, 커서, 페이드 등)는 `Singleton<T>` + `Bootstrap.cs`의 `RuntimeInitializeOnLoadMethod(BeforeSceneLoad)` 패턴으로 통일한다. 어느 씬에서 시작하든 부팅 시점에 한 번만 생성되어야 한다.

# 문서 관리

- `CLAUDE.md`는 개인 전용 설정 파일이다. 버전관리 대상에서 제외(gitignore)하고, 각자 로컬에서 자유롭게 수정한다.
- `develop.md`(개발 환경/규약), `projectinfo.md`(프로젝트 목표/기획), `contestinfo.md`(대회 개요)는 팀 공용 문서다. 버전관리 대상이며, 팀원 합의 없이 임의로 수정하지 않는다.
- `CLAUDE.md`는 공용 문서를 `@develop.md`처럼 불러와서 참조한다 — 공용 규칙은 공용 문서에만 두고 중복 기록하지 않는다.
